What it is, in one breath

LectureLoop listens to a live English lecture, shows it as text, and about every minute and a half asks one multiple-choice question about a point the lecturer has just finished. It only asks things that were actually said, and it checks the quote to prove it. At the end you get a mastery summary, and every ended lecture is saved on the device so you can come back and retry what you missed.

Ears

The microphone streams to Deepgram, which turns speech into text live.

Timing rules

Plain code decides when it's worth asking the AI: at the end of a sentence, when a question is due.

Brain

Claude decides what to ask, and writes the question plus a word-for-word quote.

Safety check + memory

Code verifies the quote is really in the transcript, then tracks answers and saves lectures on the device.

The route through the code (reference route)

This route wasn't toured live together; it's here so you can follow it whenever you like. Open the project in an editor and search for the anchors in this font.

  1. 1. A sentence ends → "maybe now?"

    lib/session/reducer.ts, search case "FINAL_SEGMENT". Each finished piece of text is added to the transcript. If it ends with ., ? or !, a counter (boundaryTick) goes up. lib/session/useLectureSession.ts reacts to that counter (maybeEvaluate("boundary") and asks the timing rules in lib/checkpoints/scheduler.ts (shouldEvaluate): warm-up done? 75 s since the last card? Is a question due (90 s)? Only then does it call the server.

  2. 2. The server asks Claude, then checks the answer

    app/api/checkpoint/route.ts → lib/checkpoints/evaluate.ts (evaluateCheckpoint) sends the recent transcript and the rules in lib/checkpoints/prompt.ts (SYSTEM_PROMPT). Claude must reply in the fixed shape from lib/checkpoints/schema.ts. Then lib/checkpoints/validate.ts (validateDecision, isGrounded) throws away anything whose quote isn't in the transcript, any repeat, or a bad set of choices, and shuffles the choices.

  3. 3. The card, the answer, and what's remembered

    components/QuickCheckCard.tsx shows the question. Tapping a choice dispatches ANSWER (reducer). lib/session/mastery.ts (deriveConcepts) turns answers into ✓ / ⚠ / ○ per concept. When you tap End, lib/session/savedLectures.ts (upsertLecture) keeps the lecture on the device for My lectures.

A practice to reuse

Report what you observed, with numbers, and let the agent find the cause. The first version looked fine in the agent's own tests. Your live tests found the real problem: "8 minutes, several ideas, one question", then "3 minutes, no question". Those concrete observations, plus the decision log (tmp/checkpoint-log.jsonl), pointed to the cause. Questions were waiting for pauses that recorded lecturers rarely make, and the test lectures had hidden this because they were split into neat sentences. The fix (sentence-based rhythm, plus test lectures fragmented like real speech-to-text) is recorded in devpost/checklist.md → Revisions, and the replay summaries show the before/after.

On a new project: write down what "working" looks like as something you can count or see, test with real input early, and when it misbehaves tell the agent what happened vs. what you expected (and how often). Leave the technical choices to the agent, but keep the decisions that change cost, accounts, or the core experience (like the question rhythm) for yourself, as you did here.

The planning trail in one paragraph

Scope set the kernel (active learning during the lecture) and the cuts (no accounts, no slides, English only). The PRD defined the screens, colors, and card behavior. The spec chose Deepgram + Claude Sonnet 5.5 + Next.js on Vercel's free plan. The build went in 7 working slices. Real tests changed three things: the question timing (twice), the card size on phones, and adding My lectures at final review.
